AGENTS.md

Guidance for coding agents working in this repository (the TypedLinearAlgebra library, git@github.com:FrancoisCarouge/TypedLinearAlgebra.git). This file is the repository root; all paths below are relative to it.

Human contributors: see CONTRIBUTING.md. AI coding agents: this file.

AI agent conduct

  • You are the author. Understand and be able to defend every line, however much a model wrote. A change nobody can explain is not ready.
  • This is a bleeding-edge C++26, concepts-and-templates codebase (the .clang-tidy Checks: '*' zero-NOLINT baseline described under Build & test assumes it). Models are weakest exactly here — watch for confident-but-wrong template metaprogramming, and build and test the change yourself rather than trusting CI or the reviewer to catch it.
  • Propose before you build for anything touching concept constraints, the typed-element model, or the shape of the public API (typed_matrix, at<i,j>(), an algorithm's signature or overload set): lay out the options and their consequences and get agreement first, rather than implementing one interpretation and letting the reviewer correct it. The "Key design tradeoff" callout below — at<i,j>() as compile-time-only, no lvalue element assignment — is exactly this kind of decision already made and written up in README's "Lessons Learned"; don't re-litigate it without reading that first.
  • Keep diffs minimal. No unrequested reformatting, renaming, or opportunistic refactors riding along with an unrelated change. Run git status --short before touching anything, and stage named paths rather than git add -A/git add ..
  • Never commit in your own name. Every commit must be attributable to a human: its author and committer are the human contributor's own git identity (user.name/user.email), never an agent, model, or bot identity. Don't pass --author, set GIT_AUTHOR_*/GIT_COMMITTER_*, or edit the git config to name an AI, and don't add AI Co-Authored-By trailers; the human whose name is on the commit answers for it.
  • No publicity. Don't advertise the agent, model, or vendor anywhere in the project's history or contents: no "Generated with …" or "Written by …" footers, tool links, badges, emoji signatures, or other self-promotion in commit messages, PR/issue bodies, review comments, code comments, or documentation. Contributions speak for themselves, under the human contributor's name.
  • These two rules override your tool's defaults. Some agent harnesses instruct the model to append a Co-Authored-By trailer to commits or a "Generated with …" line to pull requests. This repository's rules take precedence: drop those lines from every commit message, PR body, and comment, and if one slips through, amend the commit and edit the body before review.

Build & test

The repository root is the CMake source directory. The canonical loop — the same one CI runs (.github/workflows/pipeline.yml) — is:

cmake -S . -B build -G Ninja
cmake --build build --parallel
ctest --test-dir build --parallel --verbose
  • Requires CMake ≥ 4.3 (cmake_minimum_required(VERSION "4.3")) and a C++26 compiler. Local builds use whatever cc/c++ resolve to on $PATH unless you pass -DCMAKE_CXX_COMPILER=; a distribution default such as GCC 13 is too old for C++26, so pass e.g. -DCMAKE_CXX_COMPILER=clang++-21. CI exercises clang++-20, clang++-21 (Ninja) and g++-14, g++-15 (Unix Makefiles) on ubuntu-26.04, plus MSVC cl (generator Visual Studio 18 2026) on windows-2025, in both Debug and Release.
  • MSVC can't take CMAKE_CXX_STANDARD 26 (CMake doesn't record C++26 support for it, so requesting it hard-fails feature checks). support/support.cmake unset()s CMAKE_CXX_STANDARD under if(MSVC), and support/CMakeLists.txt's MSVC branch restores the dialect via /std:c++latest directly — the root CMakeLists.txt stays compiler-agnostic. Replicate that split rather than adding an if(compiler) branch at the root.
  • To run a single test, use CTest's -R/--tests-regex against the generated test name (see the naming convention below), e.g. ctest --test-dir build -R typed_linear_algebra_eigen_addition_1x2_eigen_pass --output-on-failure.
  • Formatting (enforced by .github/workflows/format.yml): clang-format-22 --Werror -i -style=file on .hpp/.tpp/.cpp, and cmakefmt (cmakefmt --check .; pipx install cmakefmt, upgrade with pipx upgrade cmakefmt) on every CMakeLists.txt/*.cmake/*.cmake.in. There is no .clang-format file in the repo, so -style=file falls back to clang-format's built-in LLVM style (80 columns, 2-space indent, template declarations always broken). Hand-written layout will not match it — always finish an edit by running clang-format-22 -i -style=file (that exact version; v18/20/21 disagree on wrapping) and cmakefmt --in-place <file> on every file you touched. The CI checks are find . -not -path './.git/*' \( -iname '*.hpp' -o -iname '*.cpp' -o -iname '*.tpp' \) | xargs clang-format-22 --Werror --dry-run -style=file and cmakefmt --check ..
  • cmakefmt reads the repository-root .cmakefmt.yaml: 80 columns and 2-space indent (its defaults), command_case: unchanged so mixed-case module commands such as FetchContent_Declare keep their spelling, and a commands: section describing the project's own pass/build/fail/bench (BACKENDS keyword) and amalgamate functions so their calls wrap keyword-aware. Declare any new project-level CMake function there too; cmakefmt --list-unknown-commands . must report none. Recursive discovery honours .gitignore, so build/ is skipped.
  • .clang-tidy runs Checks: '*' with WarningsAsErrors: '*' (minus a short denylist) — a very strict baseline; don't casually suppress warnings. .github/workflows/clang_tidy.yml configures the build with clang++-20 (-DCMAKE_EXPORT_COMPILE_COMMANDS=ON), then run-clang-tidy -p build over every benchmark|sample|support|test/*.cpp except *_fail.cpp, sharded 6 ways, using the runner's default clang-tidy (v21 as of writing, unpinned) and compile_commands.json. The codebase has zero NOLINT comments — keep it that way; rework the code instead. Gotchas that bite test files:
    • misc-include-cleaner: every std:: symbol needs its own direct #include even if transitively available (std::milli → <ratio>, std::identity → <functional>, …). .clang-tidy's IgnoreHeaders whitelists only the Eigen/mp-units/au/fcarouge/* facade headers, never the standard library.
    • google-explicit-constructor / hicpp-explicit-conversions reject any non-explicit converting constructor or conversion operator — you can't write an implicit-conversion fixture; test a shared base class instead.
    • Run it before finishing: clang-tidy-21 <file> -- -std=c++26 -Iinclude -Isupport/<backend> -Isupport/eigen <dep -isystem flags>, or run-clang-tidy-21 -p build <files> from a -DCMAKE_EXPORT_COMPILE_COMMANDS=ON build. With the Ninja generator, first build the targets of the files to lint: their compile commands reference C++ module map (.modmap) files that only exist after a build. CI uses Unix Makefiles and does not hit this.
    • No HeaderFilterRegex is set, so clang-tidy reports nothing in include/ headers, in CI or locally. Forcing --header-filter surfaces pre-existing findings (e.g. readability-redundant-declaration on the //! @name Algorithms doxygen re-declarations, and on matrix_frob_norm.tpp's forward declaration, already made by magnitude.tpp), so scope it to the header you touched: run-clang-tidy-21 -p build -header-filter='<name>\.tpp' test/<name>/<file>.cpp.
  • cmakefmt is deliberately unpinned: CI installs the latest release on every run and the pre-commit hook is a language: system hook calling whatever cmakefmt is on $PATH. Keep your local install current, or a newer release's layout changes will fail CI while passing locally; reformat with the latest release when that happens.
  • Pre-commit hooks (.pre-commit-config.yaml, run in CI by .github/workflows/pre_commit.yml): pre-commit install once per clone installs both the pre-commit and commit-msg hook types; pre-commit run -a runs everything. Covers repository hygiene (LF line endings, whitespace, case/Windows-name conflicts, large files, merge markers), gitleaks, clang-format pinned to v22 and cmakefmt (the same checks as format.yml), codespell, workflow/Dependabot/CITATION.cff schema validation, actionlint (.github/actionlint.yaml declares the ubuntu-26.04 runner label), and local checks for the SPDX Unlicense header, zero NOLINT, and the [tag] description commit-message form. zizmor (GitHub Actions security audit) is opt-in: pre-commit run zizmor --hook-stage manual -a.
    • actionlint lints run: scripts with shellcheck only when shellcheck is on $PATH, and silently skips that check otherwise — CI has it, so install it locally (apt install shellcheck or pip install shellcheck-py) or a passing local run can still fail CI.
  • Coverity Scan (.github/workflows/coverity.yml) does not gate pull requests: it runs on a schedule or manually, to stay within the service's weekly submission limit and to keep its COVERITY_SCAN_TOKEN and COVERITY_SCAN_EMAIL secrets away from pull request code. It configures with -DCMAKE_INTERPROCEDURAL_OPTIMIZATION=OFF, which support/support.cmake honors by not forcing IPO on the benchmark drivers.
  • Install: sudo cmake --install build.

Architecture

Core header

include/fcarouge/typed_linear_algebra.hpp is the single public entry point (fcarouge::typed_matrix). It declares concepts, the typed_matrix<Matrix, RowIndexes, ColumnIndexes> class template, operators, and the element_caster/cast customization point, then pulls in implementation from include/fcarouge/typed_linear_algebra/ via .tpp includes at the bottom of the header (algorithm/{add,divide,dot,equal_to,magnitude,matrix_frob_norm,matrix_inf_norm,matrix_one_norm,matrix_product,matrix_rank_1_update, matrix_vector_product,minus,product,scale,subtract,transposed}.tpp, cast.tpp, chrono.tpp, common_type.tpp, format.tpp, tuple.tpp, typed_linear_algebra.tpp, plus the non-.tpp internal/utility.hpp). typed_matrix composes (does not inherit) an underlying backend Matrix; each element's type comes from the RowIndexes/ColumnIndexes tuples, not from storage.

Key design tradeoff baked into the API (documented in-header): there is no runtime-indexed safe element access — at<i,j>() is necessarily a compile-time template API, because converting a runtime index to a dependent template type isn't possible in C++. Lvalue reference element assignment is likewise not offered; see the "Lessons Learned" section of README.md for the full rationale before trying to "fix" either of these.

Backend plug-in pattern

The library is backend-agnostic: support/<backend>/fcarouge/linalg.hpp is what test/sample code actually includes (#include "fcarouge/linalg.hpp"), and which backend's header is picked up is determined purely by which CMake target you link against — not by any #ifdef in the core library. Backends live under support/ (wired in by support/CMakeLists.txt, gated on BUILD_TESTING):

  • eigen, eigexed, nested_typed_eigen — Eigen-backed variants.
  • armadillo, armadilloxed — Armadillo-backed, mirroring eigen/eigexed. armadillo.hpp fetches Armadillo (gitlab.com/conradsnicta/armadillo-code, SOURCE_SUBDIR set to a CMakeLists.txt-less dir so its own build never runs) for headers only and compiles it with ARMA_DONT_USE_{LAPACK,BLAS, WRAPPER,ARPACK,SUPERLU,HDF5,FFTW3} — no runtime library is linked. Because solve()/inv() need LAPACK, matrix division (operator/) is unsupported with any Armadillo backend; test/division/ has no Armadillo entries and the mp_units_armadillo sample notes the gap (compare the au_std add()/subtract() omission). Facade specifics: is_armadillo keys off Armadillo's arma::is_arma_type trait (a fixed<R,C>'s CRTP base is Mat<eT>, not itself); a constrained std::formatter partial specialization plus a std::format_kind = disabled opt-out (Armadillo matrices are ranges); ADL operator==/!= returning bool in namespace arma (raw Armadillo == yields an element-wise expression). The bare armadillo backend is dropped from a few test lines where raw-Armadillo semantics differ ({{1},{4},{7}} column-literal ctor ambiguity); armadilloxed covers those.
  • au_armadillo, mp_units_armadillo, nholthaus_armadillo, chrono_armadillo — the unit-library combos over Armadillo, mirroring the *_eigen combos.
  • kokkos — Kokkos/mdspan-backed.
  • boost_multi — Boost.Multi (FetchContent of gitlab.com/correaa/boost-multi, headers only) as memory storage beneath the *_std backends, not as a composed backend: typed_linear_algebra_boost_multi only adds its include directory, and the header-less typed_linear_algebra_{au,chrono,mp_units,nholthaus}_std_boost_multi targets pair it with the matching *_std backend. test/boost_multi/ and the mp_units_std_boost_multi sample view a stack-based boost::multi::inplace_array's data_elements() through std::mdspan, and stay in the real-time context: never the heap-based boost::multi::array. Two consequences: data_elements() is a fancy offset_ptr, so pass it through std::to_address for the std::mdspan deduction guides; and a nested braced list, in construction, assignment, or as a comparison temporary, still allocates its rows as boost::multi::array, so construct from extents and a value (storage a({2, 2}, 0.);), assign a.elements() = {...} in row-major order, and verify with std::ranges::equal(a.elements(), std::array{...}). Multi names std::dextents and std::layout_stride wherever the standard library announces __cpp_lib_mdspan, which is why the fcarouge/mdspan shim imports both.
  • mp_units, mp_units_eigen, mp_units_std — mp-units (quantities/units) integration; also defines fcarouge/mp_units.hpp.
  • au, au_eigen, au_std — Au (quantities/units) integration; also defines fcarouge/au.hpp. Unlike mp-units, Au has no vector/matrix quantity representation, so fcarouge/au.hpp only needs element_caster specializations — no tuple-decomposition/disable_representation machinery. Two rough edges to know before touching Au-typed code: an unqualified matrix * bare_quantity expression can resolve to Au's own hidden-friend operator* via ADL instead of this library's, requiring an explicit fcarouge::operator*(...) call (see test/multiplication/scalar_au_eigen.cpp); and Au's Quantity::operator= is lvalue-only, which is incompatible with the add()/subtract() std::linalg-style free functions' element-compatibility check (no au_std add()/subtract() tests exist for this reason — use operator+/operator- instead).
  • nholthaus, nholthaus_eigen, nholthaus_std — nholthaus/units integration (FetchContent of github.com/nholthaus/units, or a system units package); also defines fcarouge/nholthaus.hpp.
  • chrono_eigen, chrono_std — test/sample glue for the std::chrono::duration element-type integration wired into the core header via chrono.tpp; each only defines fcarouge/linalg.hpp, there is no bare chrono target.
  • freestanding — a fixed-size matrix over a std::array, with built-in scalar types, relying only on the freestanding subset of the standard library. Its target compiles its dependents with -ffreestanding -fno-exceptions -fno-rtti on GCC and Clang (MSVC has no freestanding mode); only libstdc++ rejects a hosted-only header there, libc++ accepts every header. test/freestanding/ holds its build()-only static_assert tests, and .github/workflows/freestanding.yml cross-compiles them, and the amalgamated header, for a bare-metal Arm Cortex-M4.
  • sparse, au_sparse, chrono_sparse, mp_units_sparse, nholthaus_sparse — typed matrices over the compile-time sparsity pattern storage of SparseLinearAlgebra (FetchContent of its master, or a system fcarouge-sparse-linear-algebra package), whose patterns, storage, operations and their own tests live there. support/sparse/fcarouge/sparse.hpp only adapts it: the typed aliases typed_sparse_matrix, typed_sparse_column_vector, typed_sparse_row_vector over its fcarouge::sparse_matrix<Type, Pattern>, and the typed sparse::make_matrix<TypedMatrix>(values...), taking the 0_o literal at a structural zero. It includes SparseLinearAlgebra before the core, so that the core's qualified fcarouge::matrix_*_norm dispatch finds its norms. The aliases matrix, column_vector, row_vector are its dense pattern, so the shared test sources run on it; the backend has no tests of its own. The core names nothing specific to it. The one convention between them is generic: the member at<i, j>(value) first offers the storage its position as std::integral_constant indexes, the type of the _i literal, through tla::write_element_at, and the member at<i, j>() reads it the same way, through tla::read_element_at: a const sparse_matrix reads a compile-time position without a run-time lookup, which a run-time position, the conversion of an integral_constant included, does. Without a structural zero, a pattern has a reference-returning non-const operator[], as any dense storage. With a structural zero, it only has a const by-value operator[] and a reference-returning one for a compile-time stored position, so the core's own write_element static_assert rejects at<i, j>(value) at a structural zero and the list and tuple-like constructors at compile time, which a requires probe cannot detect. A conversion between units writes each element through that same compile-time position, and only converts into a structural zero a value the conversion keeps (tla::keeps_fixed_elements): a zero without an offset, not a temperature with one. test/division/'s and test/unit_scale/'s matrix division does not apply to it: it needs a solver.
  • main — shared CTest main() driver linked into pass/fail test executables.
  • Built-in scalar types and std::linalg need no plug-in at all.

Adding a new backend means adding a support/<name>/ directory with its own fcarouge/linalg.hpp, a typed_linear_algebra_<name> CMake target, and an add_subdirectory("<name>") line in support/CMakeLists.txt (see support/support.cmake and existing backends for the pattern).

Algorithms (include/fcarouge/typed_linear_algebra/algorithm/)

One .tpp per algorithm (add, divide, dot, equal_to, magnitude, matrix_frob_norm, matrix_inf_norm, matrix_one_norm, matrix_product, matrix_rank_1_update, matrix_vector_product, minus, product, scale, subtract, transposed), each #included near the bottom of typed_linear_algebra.hpp (alphabetically) and redeclared for documentation in the //! @name Algorithms block just below those includes (redeclaring an already-defined function — that block is the curated public API listing doxygen renders). All live in namespace fcarouge, guarded by FCAROUGE_TYPED_LINEAR_ALGEBRA_ALGORITHM_<NAME>_TPP. namespace tla = typed_linear_algebra::internal is available (aliased once in the core header; do not re-alias it in a .tpp).

Core principle: an algorithm never re-implements representation arithmetic. It (1) computes the result's row_indexes/column_indexes tuples, (2) statically checks element-type compatibility, (3) delegates the numerics to the backend via .data() (the underlying backend matrix). Prefer composing an existing algorithm over a new backend dispatch when the mathematics coincide: magnitude is matrix_frob_norm restricted to vectors.

Some algorithms have no single, uniform way to reach every backend (Eigen, Armadillo, std::linalg, ...), and instead try each backend's own spelling in turn, from most to least specific, through an internal if constexpr (requires {...}) dispatch chain ending in a static_assert(sizeof(...) == 0, "<Operation> is not supported for this linear algebra backend.") catch-all. tla::transposed (a .transpose() member, then .t(), then std::linalg::transposed), tla::dot (a .dot() member, then a recursive call for nested_typed_eigen's composed typed_matrix storage, then an ADL-found free function such as Armadillo's arma::dot, then std::linalg::dot), tla::matrix_frob_norm (an Eigen .norm() member, then the nested_typed_eigen recursion, then Armadillo's ADL-found norm(X, "fro"), then std::linalg::matrix_frob_norm), tla::matrix_one_norm (likewise, over each backend's absolute column sums), and tla::matrix_inf_norm (over its absolute row sums) are today's examples; expect more algorithms, across every rank (singleton, vector, matrix), to follow the same shape as backend coverage grows.

When such an internal dispatch helper shares its public function's name (as tla::transposed, tla::dot, tla::matrix_frob_norm, tla::matrix_inf_norm, and tla::matrix_one_norm all do) rather than being named distinctly, two precautions become load-bearing, and dropping either fails silently rather than loudly: an ambiguous or self-referential overload-resolution failure SFINAEs a requires{} branch to false instead of hard-erroring, so the dispatch just falls through to the catch-all — a build that passes but computes nothing.

  • Constrain the internal helper to the same rank/shape concept as the public function it mirrors, whenever one of its dispatch branches reaches an ADL-found free function on raw, non-typed-matrix backend storage: an unconstrained internal helper is itself a viable, equally-good candidate for that same call, tying with the ADL-found one. tla::dot's own history is the worked example: dropping this constraint silently broke every Armadillo backend.
  • Spell any recursion into composed/nested backend storage (e.g. nested_typed_eigen's typed_matrix-in-typed_matrix) fully qualified (fcarouge::<name>(...)), which needs a forward declaration of the public function placed above the internal helper in the same file: an unqualified call ties the internal helper against the public one found via ADL on the still-fcarouge-namespaced inner type — the same ambiguity, one level in.

Private helpers shared by several algorithms live once, in namespace typed_linear_algebra::internal, never as per-file copies: two same-named copies in that one namespace are a redefinition, and copies split across namespaces tie under ADL. internal/as_vector_span.hpp is the example: dot, matrix_rank_1_update, and matrix_vector_product all need the rank-two-to-rank-one reshape std::linalg wants. It is its own header, guarded on __STDC_HOSTED__ && __has_include(<linalg>), rather than part of utility.hpp, so that only the backends providing std::linalg pull in <mdspan>. Call such a helper qualified (tla::as_vector_span(...)): an unqualified call also triggers ADL on the fcarouge::typed_matrix argument, and any same-named function in fcarouge becomes a second, tying candidate, the same silent-SFINAE-to-the-catch-all failure as the fcarouge::dot recursion above.

Two deliberately mirrored API families:

  • Expression / operator style — mirrors Eigen and math notation: operator+, operator- (binary and unary negation), operator*, operator/, operator==, plus magnitude, dot, matrix_frob_norm, matrix_inf_norm, matrix_one_norm, transposed. [[nodiscard]] constexpr auto, return by value, result built with make_typed_matrix<row_indexes, column_indexes>(<backend expression on .data()>). Works on every backend. make_typed_matrix composes an element-accessible backend expression (Eigen) as-is, but materializes one that is not (Armadillo Glue/Op) through its .eval() member first, so the resulting typed matrix stays usable. dot, matrix_frob_norm, matrix_inf_norm, and matrix_one_norm return a bare element, not a typed matrix, mirroring std::linalg's own return-by-value signatures (unlike add/matrix_product/matrix_vector_product/scale, which mirror std::linalg's out-parameter signatures instead).
  • std::linalg free-function style — mirrors the std::linalg names and out-parameter signatures: add, matrix_product, matrix_rank_1_update, matrix_vector_product, scale. constexpr void f(inputs..., result&), caller pre-allocates result, body is using std::linalg::f; f(lhs.data(), ..., result.data());. Whole file wrapped in #ifdef __cpp_lib_linalg / #include <linalg> (@todo remove for native C++26), so only the *_std backends exercise them. matrix_vector_product reshapes the vector's rank-two n-by-1 storage into the rank-one span std::linalg wants through the shared tla::as_vector_span helper, which dot also uses for its own std::linalg::dot branch. transposed straddles both families: if constexpr (requires { value.data().transpose(); }) (Eigen member), else requires { value.data().t(); } (Armadillo member), else std::linalg::transposed.

Rank dispatch: overloads constrained on rank_typed_matrix<0|1|2> auto (0 = singleton, 1 = row/column vector, 2 = matrix; rank computed in utility.hpp). Singletons usually get a dedicated simpler overload plus scalar-interop overloads against the other concept (any non-typed-matrix operand), which route through element_caster / cast<underlying, T>. Constraint vocabulary lives in utility.hpp: same_as_typed_matrix, same_shape, uniform_typed_matrix, row_typed_matrix, column_typed_matrix, plus multipliable* / scalable_by in product.tpp.

Type-level index math: tla::product / tla::quotient (the multiplies / divides metafunction objects in utility.hpp, specialized over std::tuple and std::identity; std::identity is the dimensionless "1" index). Element checks are a static_assert of tla::all_of_positions<Rows, Columns> (or tla::all_of_indexes<N> for rank 1) over a predicate of the compile-time indexes, static_assert(tla::all_of_positions<R, C>([](auto i, auto j) -> bool { ...; return requires { std::declval<lhs_element>() OP std::declval<rhs_element>(); }; }), "<Operation> requires compatible element types."); add() additionally probes assignability into the result element. An element-wise check of matrices of the same shape uses tla::all_of_distinct_positions<Matrices...> instead, as +, -, and add() do: an element type is the product of its row and column index types, so it evaluates the predicate once per distinct combination of the matrices' row index types and of their column index types, and a covariance repeating a few kinds of elements over a grid costs as little as its kinds of elements. Its predicate must depend on the position only through the element types of the matrices it names. These helpers are consteval: never check elements in a tla::for_constexpr loop of static_asserts inside a run-time algorithm, which compiles a function per element, called at run time, and costs gigabytes of compiler memory and object code on a 100 x 100 matrix. Keep for_constexpr for work that is genuinely per element at run time, such as writing converted elements. matrix_product, matrix_vector_product, and the operator/ overloads still carry @todos for element verification — don't assume it is there.

Because the numerics run on the storage, whose numbers are each in their own element's unit, an algorithm computing on .data() must also require its elements to share one scale: tla::is_same_scale (utility.hpp), through a static_assert beside the element checks, or a constraint as in same_scale_terms (product.tpp). Convertibility is not enough: minutes convert to seconds, yet their numbers cannot be summed. Conversions between typed matrices keep the values instead (tla::converted_storage), or are rejected for a non-owning storage (tla::owning_storage). test/unit_scale/ covers each operation.

Checks route through the typed element access, never the raw storage: storage holds bare representation oblivious to the indexes, so verifying it directly would silently accept e.g. a length matrix vs. an area matrix whose reps happen to match (see equal_to.tpp @details); it also sidesteps backends (mdspan) whose storage type has no operator==.

scalable_by (in product.tpp) exists so the deduced-return scalar overloads stay SFINAE-friendly: an unconstrained deduced return forces the compiler to instantiate — and hard-error in — the body when third-party code (mp-units) merely requires-probes multiplication by an element type. Constrain any new deduced-return scalar overload the same way.

Known Au friction (see also the au backend note above): Au's Quantity hidden-friend operator* can win ADL over this library's, needing an explicit fcarouge::operator*(...); and Au's lvalue-only Quantity::operator= fails the add()/subtract() result-assignability probe, so those free functions have no au_std tests — use operator+ / operator- instead.

Test/benchmark generation (support/support.cmake)

Tests and benchmarks are not hand-declared per backend; four CMake functions generate them from a test name + a BACKENDS list:

  • pass(NAME BACKENDS ...) — compiles NAME.cpp once per backend and registers it as a CTest test (assertions run at static-init via main from support/main).
  • build(NAME BACKENDS ...) — compile-only (OBJECT library, EXCLUDE_FROM_ALL, no main linked); the CTest test just builds the target. Use it for static_assert-only tests such as the concept checks in same_as_typed_matrix/, nested/, underlying/.
  • fail(NAME BACKENDS ...) — same shape as pass, but expects a compile failure (EXCLUDE_FROM_ALL target invoked via cmake --build --target, WILL_FAIL TRUE).
  • bench(NAME SIZE BACKENDS ...) — configures NAME.cpp → NAME_SIZE.cpp and registers a nanobench-based benchmark.

Generated target/test names follow typed_linear_algebra_<backend>_<dir>_<name>_pass (pass and build both use the _pass suffix; ..._<name> for fail, ..._<name>_<size>_bench), where <dir> is the calling directory's name. Those are CTest names; the build targets append _driver, and a build() target is ..._<name>_build_driver, so build a test with e.g. cmake --build build --target typed_linear_algebra_<backend>_<dir>_<name>_pass_driver. test/ is organized one directory per operation/feature/concept — addition/, assign/, at/, common_with/, constructor/, copy/, distinct/, division/, element/, equal_to/, format/, magnitude/, matrix_frob_norm/, matrix_inf_norm/, matrix_one_norm/, matrix_product/, matrix_rank_1_update/, matrix_vector_product/, minus/, mp_units/, multiplication/, nested/, operator/, row_typed_matrix/, same_as_typed_matrix/, scale/, sparse/, structured_bindings/, subtraction/, transposed/, underlying/, unit_scale/ — each with its own CMakeLists.txt listing pass(...)/build(...)/fail(...) calls per test file and backend combination (some dirs, e.g. element/ and row_typed_matrix/, mix build() concept checks with fail() cases); test/CMakeLists.txt itself only add_subdirectorys them. Follow that pattern when adding a new test case rather than writing a bespoke add_test.

Test files themselves are minimal: #include "fcarouge/linalg.hpp", then a single [[maybe_unused]] const auto test{[] { ...; assert(...); return 0; }()}; block inside namespace fcarouge::test { namespace { ... } } — no test framework, just <cassert> run at static-init time via main from support/main.

Every test, sample, and benchmark is real-time verified by default: built with -fsanitize=realtime (the Real-Time job of sanitizer.yml), the typed_linear_algebra_realtime object in support/main (realtime.cpp, linked through typed_linear_algebra_main, and directly by bench() and plot) runs the whole program in a real-time context, as if its entry point were [[clang::nonblocking]], so a memory allocation, lock, or blocking input-output call aborts it. An entry point that genuinely cannot be real-time (it formats, prints, or benchmarks) opts out explicitly: #include "fcarouge/realtime.hpp" and declare const not_realtime opt_out; as the first statement of its test/sample lambda, or const fcarouge::not_realtime opt_out; first in a benchmark's main. Never opt out to silence a finding in code meant to be real-time. Without the sanitizer the token does nothing.

Concept checks that inspect element types (uniform_typed_matrix, element/, and tla::locatable_by behind at<Type>()) have traps — tla::locatable_by especially, because it runs std::is_convertible from every element type to the requested type:

  • In a two-index matrix<Rep, RowIndexes, ColumnIndexes> an element's type is RowType * ColType (tla::product). That product must be well-formed for every row/col index pair, so keep std::identity (via std::tuple<std::identity>) on one axis — product<duration, duration>, product<year, month>, etc. are ill-formed and hard-error.
  • Au: checking is_convertible between two same-dimension quantities of different representation (QuantityD vs QuantityI, i.e. a float→int rep conversion, as at<QuantityI>() on a QuantityD element does) instantiates Au's overflow_boundary.hh, whose ValueOfMaxFloatNotExceedingMaxInt::max_mantissa has a local ONE that shadows au::ONE — MSVC C4459, fatal under /WX. Compare quantities of the same representation (different unit, e.g. Meters vs Kilo<Meters>, is fine); if a rep-conversion test is unavoidable, add /wd4459 to support/au/CMakeLists.txt next to the existing /wd4244.

A footprint() line measures both variants against the same criteria, so a typing cost fails it; a line with VARIANT "typed" or VARIANT "storage" measures that variant alone, for the equality, which has no storage operation, and the product, whose typed result is copied once more than its storage's (to be removed, then paired). Recipe: adding an algorithm

  1. Header. Create include/fcarouge/typed_linear_algebra/algorithm/<name>.tpp: verbatim Unlicense SPDX block, include guard FCAROUGE_TYPED_LINEAR_ALGEBRA_ALGORITHM_<NAME>_TPP, namespace fcarouge. Choose the API family — operator/expression (works on every backend) or std::linalg free function (wrap the whole file in #ifdef __cpp_lib_linalg + #include <linalg>, use the void f(inputs..., result&) out-parameter signature). When std::linalg has the operation, mirror its name and semantics and add //! @see std::linalg::<name>; otherwise mirror Eigen/common nomenclature (README already tracks the mapping). The family follows the signature, not the name's origin: a std::linalg algorithm returning by value (dot, matrix_frob_norm) needs no #ifdef __cpp_lib_linalg wrapper and reaches every backend through an internal dispatch chain (see Algorithms above), guarding only its std::linalg branch with #if __STDC_HOSTED__ && __has_include(<linalg>). For an Armadillo branch, check the call needs no LAPACK (norm(X, "fro") does not, the default matrix norm(X) does), since the Armadillo backends link none. Check each backend call's semantics on one-row and one-column inputs too: a backend may silently switch to a vector norm there, as Armadillo's norm(X, 1) does, returning a row vector's sum of absolute elements instead of its matrix one norm; Eigen's lpNorm<1>() is that element-wise sum for every shape. Armadillo's norm(X, "inf") and Eigen's lpNorm<Eigen::Infinity>() likewise return the largest absolute element where the matrix infinity norm of a row vector is its sum of absolute elements.
  2. Overloads per rank. Provide rank_typed_matrix<2>, <1>, <0> overloads as the operation admits, or a single rank-generic overload when the backend call is (e.g. uniform_typed_matrix auto); a rank-generic body must name elements with tla::element_at<matrix, i, j>, since the element<...> member template is rank-checked; add other-operand overloads for scalar interop (route values through cast<underlying, T>). Constrain any deduced-return scalar overload on scalable_by or an equivalent requires so it stays SFINAE-friendly.
  3. Result type. Compute row_indexes / column_indexes with tla::product / tla::quotient over the operand index tuples, then return make_typed_matrix<row_indexes, column_indexes>(<expression on .data()>) — or write into result.data() for the free-function family.
  4. Element checks. A static_assert of tla::all_of_distinct_positions<lhs_matrix, rhs_matrix> for an element-wise operation on matrices of the same shape, otherwise of tla::all_of_positions<rows, columns> (or tla::all_of_indexes<rows * columns> for rank 1) over a captureless predicate returning requires { std::declval<lhs_element>() OP std::declval<rhs_element>(); }, with the message "<Operation> requires compatible element types.", one static_assert per message; also assert result-element assignability for out-parameter algorithms. Add same_shape / size static_asserts as the math requires.
  5. Wire into typed_linear_algebra.hpp. Add the #include "typed_linear_algebra/algorithm/<name>.tpp" line (alphabetical, with the rest) and a matching, undocumented forward re-declaration in the //! @name Algorithms block below the includes. The @brief/@details/@see/@todo doxygen lives once, on the definition in the .tpp. Also list the new .tpp in the FILE_SET of include/CMakeLists.txt, or it is not installed; nothing checks this list.
  6. README. Add a row to the "Operations" table.
  7. Tests. New test/<name>/ directory (or reuse an existing operation dir) with its own CMakeLists.txt (SPDX comment block, then fail(...) lines then pass(...) lines), and an alphabetical add_subdirectory("<name>") in test/CMakeLists.txt. test/CMakeLists.txt only aggregates — never a bespoke add_test.
    • File naming: <shape>[_<backend>][_fail].cpp — 1x1 singleton, 1x2/2x1 vectors, 2x2/2x3/3x2 matrices, RxC_R'xC' for products, plus semantic names (row, column, scalar, matrix_rhs, vector_lhs, rank_mismatch). Generated test name: typed_linear_algebra_<backend>_<name>_<file>_pass.
    • Backends & types to cover: expression-style → eigexed, nested_typed_eigen, armadilloxed with plain double (the bare eigen and armadillo backends alias matrix to the raw, untyped backend matrix, so they only fit tests of the operators' raw semantics, never a typed-only algorithm), each *_eigen unit backend's *_armadillo twin, plus au_eigen, mp_units_eigen, chrono_eigen, nholthaus_eigen for typed elements; std::linalg-style → au_std, mp_units_std, chrono_std, nholthaus_std only (they need <linalg>/<mdspan> storage). Cover at least one plain and two unit backends, and one mixed-type vector (e.g. position, velocity) to prove per-element typing. chrono also exercises semantic rejection (time_point + time_point must not compile).
    • Discriminating values: pick operands for which each plausible wrong implementation gives a different answer: negative elements for an absolute value, a non-square matrix for a row/column mix-up, a row vector for a backend's vector-norm special case. A symmetric, all-positive {{1, 2}, {2, 4}} hides all three.
    • pass body: the standard static-init form — [[maybe_unused]] const auto test{[] -> int { ...; assert(...); return 0; }()}; inside namespace fcarouge::test { namespace { ... } }, #include "fcarouge/linalg.hpp" + <cassert> + backend unit headers, with a //! @test one-liner on top. Assert the numeric result and the result type (static_assert(std::same_as<decltype(r)::row_indexes, ...>)), across the accessor forms (.at<i>(), .at<i_i>(), [i_i], (i_i)) where relevant.
    • fail test per rejected shape/rank/type mismatch: keep the correct line as an // Intended: comment directly above the broken one; fail(...) sets WILL_FAIL.
    • Use build(...) instead of pass(...) for static_assert-only tests. A requires probe at namespace scope hard-errors instead of yielding false on substitution failure, since it is not in a template: wrap a negative probe (not requires { f(bad); }) in a test-local concept.
    • WILL_FAIL accepts any compile error, so build each fail target once and read its diagnostic to confirm it fails for the intended reason, not a typo or a missing include.
  8. Sample (optional): extend an existing sample, or add a sample/<name>.cpp wired by hand in sample/CMakeLists.txt (add_executable, target_link_libraries, add_test), if the algorithm is user-facing and illustrative.

Conventions

  • Header-only library: keep the public API under include/fcarouge/; implementation details belong in typed_linear_algebra/ and are not part of the public surface.
  • Internal implementation details live in namespace fcarouge::typed_linear_algebra::internal — the single internal namespace, mirroring the include/fcarouge/typed_linear_algebra/internal/ directory. Never introduce fcarouge::internal, fcarouge::typed_linear_algebra_internal, or any other parallel internal namespace; nest an algorithm's private dispatch helpers inside namespace typed_linear_algebra::internal { ... } within namespace fcarouge, and refer to them through the tla alias (tla::dot(...), fcarouge::tla::for_constexpr outside fcarouge) — an unqualified internal:: does not resolve from fcarouge scope. Spell out typed_linear_algebra::internal only where the alias cannot be used: reopening the namespace, utility.hpp and code including only it, and the alias declaration itself, declared once in the core header and never re-aliased in a .tpp.
  • The core header stays freestanding: no hosted-only standard header, no exception, no run-time type information, no memory allocation. A hosted-only feature fences its own file content, includes included, under #if __STDC_HOSTED__ inside its include guard, as chrono.tpp and format.tpp do, so the core header includes it unconditionally. Guard on __STDC_HOSTED__ or a feature-test macro, never on __has_include alone: a freestanding standard library ships its hosted-only headers too, which reject their inclusion.
  • Every source/CMake file carries the Unlicense SPDX header block — copy it verbatim (version/URL match the root CMakeLists.txt) into any new file.
  • The public CMake target consumers link against is fcarouge-typed-linear-algebra::tlinalg; the package name is fcarouge-typed-linear-algebra.
  • The author writes precise, terminology-careful @note/@todo/@warning doxygen comments explaining design rationale directly in headers — match that register when editing docs/comments rather than simplifying.
  • Public documentation states the contract and its rationale, not the implementation: what the function means, what it accepts or rejects and why, never which internal helper, backend member, or dispatch order computes it ("Delegated to the backend via `tla::dot`" does not belong in a public @details). Implementation notes belong on the internal helper itself, in typed_linear_algebra::internal, or in a plain // comment at the code they explain.
  • Blank lines separate groups of statements, not individual statements. A group is a run of consecutive statements of one kind and one purpose, with one blank line between groups, so a test reads as vocabulary, constants, construction, assignment, verification. Kinds that each form their own group: includes of the same origin; using-declarations and type aliases; constant declarations (constexpr auto m2{au::squared(m)};); the declaration and initialization of related objects (a backing storage, its std::mdspan, and the typed matrix over it); a run of element assignments; a run of checks. Never interleave kinds within a group: declare every using-declaration and alias first, then the constants derived from them, even when that moves a constant below aliases it does not depend on. Within one kind, split a run when its parts serve distinct roles, for example element types and the matrix types built from them, rather than merging everything that shares a syntactic form.

  • Uniform initialization, also known as brace initialization, is used as much as possible, in the library, its support, tests, samples, benchmarks, and documentation alike: braces read the same for every kind of initialization, reject narrowing conversions, and are never parsed as a function declaration. Brace a variable or constant (const auto value{expression};, for (std::size_t i{0}; ...)), a structured binding (auto [x, y, z]{velocity};), a constructor member initializer, a default member initializer, a variable template definition or specialization (constexpr range_format format_kind<Type>{range_format::disabled};), and an explicitly typed temporary or conversion (To{value}, vector3d{1, 2, 3}, std::make_index_sequence<Size>{}, the decay-copy auto{...}). A default-constructed object whose type initializes itself stays default-initialized, without braces, the simpler syntax: const not_realtime opt_out;, a typed matrix (matrix<representation, indexes, indexes> value;, zero-initialized by its default constructor), the freestanding backend's matrix result; (zero-initialized elements), a standard container or string. Write T value{}; only where default-initialization would leave a value indeterminate that is read before it is written: a scalar, or an aggregate or backend matrix (Eigen::Matrix) not fully assigned first: Eigen::Matrix<representation, 2, 2> storage; needs no braces when storage << 1., 2., 3., 4.; assigns every element next. Parentheses or = remain only where braces would change the meaning; keep them there and, where it is not evident, say why in a comment:

    • A type whose std::initializer_list constructor braces would select instead: std::vector<double> storage(Size * Size); is Size * Size elements, storage{Size * Size} one; Boost.Multi's storage a({2, 2}, 0.); is a two-by-two array, see the boost_multi backend above.
    • A conversion that may narrow, for example an int element of a list or tuple to a double matrix element, which braces reject: the element conversions of the list-of-lists and tuple-like constructors, const element_type converted = value; and const element<i> converted(get<i>(value));.
    • A test of copy-initialization itself, the implicit conversion an = exercises and braces would bypass: const velocities state = value; in test/mp_units/unit_conversion.cpp, next to its explicit, braced counterpart.

    A function call, a factory (make_typed_matrix<...>(...)), or a named cast (static_cast<storage_index>(row)) is not an initialization and keeps its parentheses.

  • An unused function parameter keeps its name in the signature, never commented out as /*name*/, and the body discards it with static_cast<void>(name); as its first group of statements: the name documents the parameter where the API is read, and the cast states the decision not to use it. A declaration without a body names the parameter too. Where the name would redeclare a local, rename the local rather than the parameter.
  • Class members follow the conventional order, as far as the language allows, so that a reader meets the interface before the implementation: the public section first, with its nested types, type aliases, and constants, then its constructors, assignment operators, and destructor, then its member functions; the protected section next, with the functions and hooks intended for derived classes; the private section last, with its helper member functions, then its static and non-static data members, ordered for their initialization dependencies or memory alignment. A data member that must stay public, an aggregate's, opens the public section with the types and constants, as the elements of the freestanding backend's matrix do. A declaration sees only the names declared above it, whereas a member function body sees the whole class: a member type that a public signature or constraint names is itself public and first, as the matrix alias of the std::formatter specialization, and the private members a body uses, such as the storage of typed_matrix or the rows and columns of the formatter, stay last.
  • Commit messages follow [tag] short imperative description — a lowercase bracketed tag naming the area touched ([test], [cicd], [documentation], [support], [algorithm], [benchmark], ...; git log --oneline has the established vocabulary). Match it rather than inventing Category: ... or type(scope): styles.
  • PR/issue bodies and other GitHub-rendered Markdown use hard line breaks — a newline in the middle of a paragraph renders as <br>, so wrapped prose arrives as a ragged column. Write one paragraph per line there.
  • Keep PR descriptions concise: what changes and why, in a sentence or a short paragraph. Don't restate the diff, list the files touched, or add summary, test plan, or checklist sections: the diff and CI already show them.
  • Gate a new constraint on the exact precondition the code depends on, never on an adjacent capability or a property specific types merely happen to share. scalable_by (product.tpp) is the pattern to copy: an unconstrained deduced-return scalar overload would hard-error — instead of failing SFINAE — the moment third-party code (mp-units) merely requires-probes it.
  • No one-letter lowercase locals or parameters in test/sample code. au::symbols, mp_units::si::unit_symbols, and nholthaus/units all export single-letter names (m, s, A, N, ...) that test files pull in with using ...::m;; a same-named local shadows it and MSVC reports it (C4456–C4459), fatal under /WX — the same failure mode already called out above for Au's ONE in overflow_boundary.hh. Use descriptive names, or lhs/rhs for a binary operator's two sides.
