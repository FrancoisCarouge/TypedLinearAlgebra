# BUG

Shortcomings, frictions and improvement opportunities in TypedLinearAlgebra, found while integrating it with [FrancoisCarouge/Kalman](https://github.com/FrancoisCarouge/Kalman) into [ArduPilot](https://github.com/FrancoisCarouge/ardupilot/tree/fcarouge). Copied from the TypedLinearAlgebra findings of the integration's [findings table](https://github.com/FrancoisCarouge/ardupilot/blob/fcarouge/docs/FCAROUGE_FINDINGS.md), which keeps the numbering and the Kalman-only findings.

Status: open (not reported upstream yet), reported, fixed (with the upstream version).

All findings were rechecked on 2026-10-09 against Kalman ae8146d7b, TypedLinearAlgebra c9a5c2b and mp-units 132b590d2; those not annotated otherwise are unchanged.
On 2026-10-11 the changes up to Kalman ad6ea6dc9 and TypedLinearAlgebra 1b91a3678 were examined: F32 is fixed, F28 is partly addressed, and F36 to F38 are new.
On 2026-10-13 the open findings were rechecked in the sources of Kalman f897f39c8 and TypedLinearAlgebra ac4c3567a: none is closed; the stack probe of F38 gives the same frames.
Library versions examined: Kalman `2fbb1e2`, TypedLinearAlgebra `8eb0b1c` (2026-10-05).

| F18 | Both | Usability | The backend contract includes divisions that only form types: Kalman takes `state / state` (transition matrix type) and `scalar / state` (output model type for a scalar output). TypedLinearAlgebra's `operator/` deduces its return type, which instantiates the backend division body even in type-only contexts, so a backend cannot declare these as unsupported: it must implement non-square right division (Eigen-like minimum norm / least squares semantics). Undocumented. | `x_z_p_q_r_hh_f_us_ps.hpp` deduction, `divide.tpp`; a `static_assert` in the backend's non-square branch fired. | Compute these types without evaluating a division (type traits), or document the full division contract. | open |
| F19 | TLA | Usability | Withdrawn, inaccurate. The element setter is `at<i...>(const element &)`, at the pinned and later versions: temporaries, `const` values, equivalent unit expressions such as `(m/s) * m^2 / m^3` for `1/s`, and other units of the same dimension (km for m) are accepted, a wrong dimension is rejected. The named variables in the thermal EKF were a workaround for F20 (single index access on a 1x4 matrix), misattributed here. | Re-tested 2026-10-09 with g++ 15 on TypedLinearAlgebra 8eb0b1c and c9a5c2b; the thermal EKF output model now sets elements from temporaries. | None. | withdrawn |
| F20 | TLA | Usability | A 1xN or Nx1 typed matrix is rank 1 and rejects two-index access (`element<0, j>`, `at<0, j>`) through a sentinel type with deleted special members; the error is "use of deleted function ~type()". Generic filter code (an output model is z x n) breaks when the output count is 1. Likewise a 1x1 typed vector is rank 0 and rejects `at<0>()`, requiring `at()`. | Thermal EKF output model, 1x4; again generic element type traits in `AP_LinearAlgebra` (`ElementType`), which must dispatch on the shape because `element<i, j>` is unusable on vectors.; also the cause of the thermal EKF's named element variables first attributed to F19; 2026-10-11: a quadratic form `transposed(y) / S * y` is a 1x1 typed matrix, not its element, read with `at()` | Allow full-rank indexing on vectors (index 0 on the unit dimension), or a readable `static_assert`. | open |
| F22 | Both | Build | Compile cost per translation unit (g++ 15, `-O2`): `kalman.hpp` 2.2 s / 154 MB, `typed_linear_algebra.hpp` 2.1 s / 185 MB (about 1.3 s of each is `<format>`/`<print>`, see F2), with TypedLinearAlgebra's mp-units support 5.8 s / 383 MB. | F25 | TLA | Build | `typed_matrix::data()` returns `std::forward_like<decltype(self)>(self.storage)`. With clang (20, 21) and Ubuntu 24.04's default libstdc++ 14.2, whose `std::forward_like` has a deduced `decltype(auto)` return type, this fails: "function 'forward_like<...>' with deduced return type cannot be used before it is defined". libstdc++ 14.3 and 15 rewrote it with an explicit return type and work. | CI `test unit tests and sitl building (clang, ...)` on `test_linear_algebra`; libstdc++ `bits/move.h` 14.2 versus 14.3. | Avoid `std::forward_like` (an explicit cast on the deduced `self` category), or document libstdc++ >= 14.3 for clang. | open |
| F26 | TLA | Features | No typed block, segment or concatenation operations: a heterogeneous state vector such as EKF3's 24 states is used by groups (velocity, position, biases), and covariance updates work on blocks, but TypedLinearAlgebra only offers element access (`at<i>()`) and whole-matrix algorithms. Mapping EKF3's union of a state struct and a `Vector24` onto one typed vector would need per-element code. Nested typed matrices (`support/nested_typed_eigen`) may be the intended route; undocumented for this use. | TypedLinearAlgebra public API and README; EKF3 `state_elements`.; 2026-10-11: the EKFGSF innovation variance is the velocity block of the covariance plus R, the dense `H * P * transposed(H) + R` with a selector H, for want of a block, cost stack (F38), so ArduPilot reads the four elements as quantities; 2026-10-13: an EKF3 observation Jacobian has 2 to 6 non-zero elements of 24 (5 for the true airspeed), which the generated code exploits and a dense typed row cannot: `P * transposed(H)` and `H * P` do 24 terms per element instead of 5 | Typed `block<Row, Column, Rows, Columns>()` views or copies with their element types, and concatenation of typed vectors, or documented guidance for grouped states. A typed selection of rows or columns by a compile-time index list would serve both the grouped states and the sparse Jacobians. | open |
| F27 | TLA | Usability | A unit mismatch is reported as "Matrix addition requires compatible element types" without the position or the two element types involved; in a 9x9 normal matrix the developer must guess which element is wrong. | Deliberate mistake in the accelerometer calibrator (a unitless residual) in `add.tpp:86`. | Report the first incompatible position and both element types, for example with a per-element `static_assert` in an index-expanded check. | open |
| F28 | TLA | Embedded | No compound assignment (`+=`, `-=`, `*=`) and no in-place algorithms: every typed operation returns a new matrix, and the wrappers copy whole backend matrices. `JTJ = JTJ + transposed(J) * J` on 9x9 floats needs a 1336 B stack frame on Cortex-M7 (ArduPilot limit 1300 B, `-Werror=frame-larger-than`), where the hand-written loop needs none beyond JTJ. ArduPilot works around it by type-checking the expression with an unevaluated `decltype` and accumulating on the backend storage. | `AP_AccelCal/AccelCalibrator.cpp` (CubeOrange, MatekF405 builds); again in `AP_Compass/CompassCalibrator.cpp`, where JTJ is also damped in place twice instead of copied, to fit the 2048 B calibration thread stack.; 2026-10-11: TypedLinearAlgebra 1b91a3678 adds an in-place `matrix_rank_1_update(x, y, a, a)`, exactly the accumulation needed, next to `add`, `matrix_product` and `scale`, but these exist only under `__cpp_lib_linalg` and delegate to `std::linalg` over `mdspan`: unavailable with libstdc++ 14 and 15, Arm GCC 15.2, and an owning backend such as ArduPilot's, so the workaround stays; 2026-10-13: for one scalar fusion on a 24-state typed covariance (EKF3), `P = P - K * transposed(PHt)` takes a stack frame of 9528 bytes in single precision and 19048 in double on Cortex-M7, against 608 and 1200 with the update done in place on the storage | Compound assignment operators delegating to the backend's in-place operations, and move/forwarding through `make_typed_matrix` so temporaries are not copied. Offer the in-place algorithms without `<linalg>`, through a backend dispatch as `transposed` has. | open, partly addressed |
| F29 | TLA | Embedded, build | `typed_linear_algebra.hpp` always includes the `std::chrono` integration (`chrono.tpp`, `<chrono>`) and `<format>`. | F30 | TLA | Portability | Does not compile with the libc++ of current LLVM (emscripten 6.0.8, clang 24), even for a 2-element mp-units vector: `typed_matrix` reads `std::tuple_size_v<row_indexes>` (`typed_linear_algebra.hpp:195`); TypedLinearAlgebra's `std::tuple_size` specialization for typed matrices is constrained by concepts (`rank_typed_matrix`, `same_as_typed_matrix`) whose `std::same_as` instantiates the `std::tuple`; libc++'s C++23 tuple-like `operator<=>` then needs `tuple_size_v` of that same tuple, whose initializer is still being evaluated: "non-type template argument is not a constant expression" (`tuple:344`). Completing the index tuples beforehand avoids it for user-visible types, but not for the tuples TypedLinearAlgebra computes internally (products, quotients, `make_typed_matrix` in `typed_linear_algebra.tpp:362`). Native clang 20/21 with their libc++ and libstdc++ 14/15 are not affected yet. Pinning an older emscripten is no way out: 4.0.20 fails earlier, in mp-units `master` (`absolute_zero` does not satisfy `PointOriginFor`), which TypedLinearAlgebra requires (F13). | ArduPilot `test WebAssembly Plane` CI and local emscripten 6.0.8 build of the typed accelerometer calibration; minimal reproducer with `ColumnVector<float, m/s^2, 1>`.; again with emscripten 6.0.8 (CI version) on the Kalman soaring EKF, `objs/AP_Soaring` | Constrain the `std::tuple_size` specialization without instantiating arbitrary tuples (for example on a cheap trait of the `typed_matrix` template), and add an emscripten or libc++-trunk CI job. | fixed (TypedLinearAlgebra c9a5c2b: WebAssembly Plane with emscripten 6.0.8 builds with the thermal EKF and the accelerometer, compass and polynomial fits) |
| F31 | TLA | Features | No typed diagonal operations: extracting the diagonal of a heterogeneous square matrix as a typed vector, building a typed diagonal matrix from a typed vector, or adding a typed vector to a diagonal. These are what dimensionally consistent least-squares damping (Marquardt's lambda * diag(J^T J)) and covariance regularization need; the "identity" of a heterogeneous normal matrix has diagonal elements of different units, so `one<>`-style identities do not apply. | ArduPilot `CompassCalibrator` Levenberg-Marquardt damping (see the plan, Phase 6): the port adds lambda to the backend diagonal in place, outside the type system. | `diagonal(m)` returning a typed vector of the diagonal element types, `diagonal_matrix(v)`, and `add_to_diagonal(m, v)`. | open |
| F32 | TLA | Correctness | Matrix division `a / b` derives its result type from the first column index of `a` and of `b` only, without checking that `x * b` has the type of `a` (`@todo Add type verification` in `divide.tpp`): a dimensionally inconsistent equation compiles and yields a wrongly typed result. There is also no way to choose the decomposition (symmetric positive definite normal matrices, the common case, suit Cholesky without pivoting, cheaper on stack and with a unit-consistent singularity test). | A test dividing a unitless row by a normal matrix in m^2, m*s, s^2 compiled with a unitless result; `AP_LinearAlgebra::divide_positive_definite()` now checks the product element by element. | Verify division with the product's type rules (a `static_assert` on `x * b` against `a`); offer a division or solve that names its decomposition. | fixed (TypedLinearAlgebra 1b91a3678: the division is verified element by element and the units of the quotient come from both operands; the same unitless row over a normal matrix now fails with "Matrix division requires compatible element types", and ArduPilot's own check is removed). Choosing the decomposition is still not possible |
| F33 | TLA | Features | All elements of a typed matrix share the backend's scalar type: the mp-units plug-in requires each quantity's representation to equal the storage type. A state that mixes precisions, such as ArduPilot's `[position, velocity, acceleration]` with a `double` position (`postype_t`, for metre-level resolution far from the origin) and `float` velocity and acceleration, cannot be one typed vector without widening every element to `double`. | Probe: `ColumnVector<double, quantity<m, double>, quantity<m/s, float>>` and the `float` storage variant both fail the `element_caster` static assertion (TypedLinearAlgebra c9a5c2b). | Allow per-element representations (a tuple-like backend, or storage of the common type with exact per-element casts), or document the single-representation requirement. | open |
| F34 | TLA | Usability | A heterogeneous two-dimensional typed matrix has no element list constructor: the variadic constructor requires a vector, and the `initializer_list` of rows a uniform matrix.
